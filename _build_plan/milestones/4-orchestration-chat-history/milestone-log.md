# Milestone 4 — Orchestration chat + history log

## What's new in the app

- **Every work item now has a chat panel**, sitting beside the item so you can read it while you talk. Ask about the item in plain language and get an answer.
- **The agent's reply streams in** as it's written, rather than appearing all at once after a wait.
- **You can tell the agent to change things** — status, priority, owner, or the Roadmap/PRD/Spec text — and it does it, then says what it changed and from what to what.
- **The agent can only do what you can do.** If a Product Manager asks it to rewrite the Spec, it refuses, exactly as the PM's own edit would be refused. Chat is not a way around role rules.
- **A new History tab records every change** to a work item: which field, the old value, the new value, who or what changed it, why, and when.
- **History covers everything, not just chat** — edits typed into a form, cards dragged on the board, and content generated by the agent all appear in the same list.
- **You can tell AI-written content from hand-written content.** Applied drafts are recorded as written by the agent and approved by a named person.
- **Chat history sticks around** — reopen a work item later and the conversation is still there.

## What was built

**Schema** (`src/db/schema.ts`, migration `0002_sleepy_justice.sql`)
- `chat_role` (`user | assistant`) and `change_actor` (`user | agent`) enums.
- `chat_message`: work item, role, content, `userId` (null on assistant turns), timestamp.
- `change_log_entry`: work item, field, old/new value, `actorType`, `actorUserId`, `why`, timestamp. Both cascade from `work_item`.

**Write layer** (`src/lib/work-item-writes.ts`) — `applyWorkItemCore`, `applyStatusChange`, `applyRoadmap`, `applyPrd`, `applySpec`. Each reads current values, writes, and records the diff.

**Change recording** (`src/lib/changes.ts`) — `recordChanges()` plus the `ChangeActor` type. Only fields that actually differ are written.

**Field labels** (`src/lib/field-labels.ts`) — display names, deliberately separate from `changes.ts` (see decision 3).

**Orchestrator** (`src/lib/ai/orchestrator.ts`) — `buildContext()` assembles the system prompt (item, all three altitudes, recent history, people); `buildToolImpls()` provides the six write tools; `TOOL_SCHEMAS` / `TOOL_DESCRIPTIONS` define them.

**Chat route** (`src/app/api/work-items/[id]/chat/route.ts`) — streams NDJSON. Uses `client.beta.messages.toolRunner` with `stream: true` and `betaZodTool`.

**Stub chat** (`src/lib/ai/stub-chat.ts`) — the no-API-key path.

**UI** — `chat-panel.tsx` (streaming thread, tool notes, auto-scroll), `history-tab.tsx`, and `work-item-detail.tsx` reworked into a two-column layout with History as a fourth tab.

**Rewired** — `updateWorkItemCore` / `updateRoadmap` / `updatePrd` / `updateSpec` and the board's `moveWorkItem` now delegate to the write layer. New `applyGeneratedDraft` action.

## Decisions made during implementation

1. **The write layer lives outside `"use server"`, and this is load-bearing.** Every export of a server-action file is callable by the browser. The `applyX` functions take an `actor` argument, so exporting them from `actions.ts` would have let any client POST a forged `{type: "agent"}` actor and fabricate history entries. They live in `src/lib/work-item-writes.ts`; server actions and the chat route wrap them and resolve the actor from the session. **Do not move them into a `"use server"` file.**

2. **The agent inherits the caller's permissions.** Tools call `canEditAltitude(caller.role, …)` before writing and return a refusal string the agent relays. Any other design would make chat a role-gate bypass — a PM could simply ask the agent to rewrite the Spec.

3. **`fieldLabel` had to be split out of `changes.ts`.** The History tab renders inside a client component, and `changes.ts` imports the database. The production build failed with `postgres` being pulled into the browser bundle. Pure display constants now live in `src/lib/field-labels.ts`. Worth remembering for any other shared helper the client touches.

4. **`why` is recorded for chat and generated content, not manual edits.** Confirmed with the user. Agent changes store the user's message as the reason; applied drafts store "Generated draft, approved by the user"; manual form saves record no reason, because adding a note field to every form would tax every save.

5. **Reading is context, not tools.** The system prompt carries the item, all three altitudes, the last 20 history entries, and the user list. The agent answers without a round trip, and it cannot read outside this work item.

6. **`applyGeneratedDraft` trusts the client's claim.** It marks content agent-written/user-approved, and a user could call it directly to mislabel their own typing as agent-written. That is an attribution wrinkle, not an escalation — the same altitude gate applies either way. Tightening it would mean persisting drafts server-side and applying by id.

7. **The stub understands a few fixed phrasings** (`set priority to high`, `move to done`, `assign to <email>`, "update the prd/spec") and calls the same tools the real agent would. Without that, the PRD's central criterion — ask for a change, see it in History — could not be verified without an API key.

8. **Streaming is NDJSON over a route handler**, not a server action (server actions can't stream). Events: `text`, `tool`, `error`, `done`. The client splits on newlines and keeps the partial tail.

## What the next milestone needs to know

- **Build runs should log to history too.** `recordChanges()` with an `agent` actor is the mechanism; a status move to In Progress / In Review should go through `applyStatusChange` so it lands in History like every other change.
- **`applyStatusChange(input, actor, why)`** is how milestone 5 should move cards automatically — not a direct `db.update`, or the change won't be recorded.
- **Adding a tool to the agent** means: a Zod schema in `TOOL_SCHEMAS`, a description in `TOOL_DESCRIPTIONS`, an implementation in `buildToolImpls`, and an explicit `betaZodTool(...)` entry in the chat route. The entries are written out one by one on purpose — mapping over the schema record collapses the input types to a union and fails to typecheck.
- **`ANTHROPIC_API_KEY` now drives two paths** — structured generation (`src/lib/ai/client.ts`) and streaming chat (the route). Both fall back to stubs in development and throw in production.
- **The detail page is a two-column grid.** New panels go in the left column; the right column is the chat.

## Deviations from the PRD

- **The "why" note is chat-only** (decision 4) rather than available on manual edits. The PRD's wording allows for a note on manual changes; we chose not to add the field yet.
- **Chat is a side panel, not a tab.** The PRD says "chat panel"; the layout became two-column so the item stays readable while chatting.
- Everything in "What gets built" was delivered. Nothing was cut.

## Verification

Verified in headless Chrome on a clean database — 12 checks, all passing, no console errors:

| Done-when criterion | Result |
| --- | --- |
| Open the chat panel and ask a question | Pass — answered from context, streamed in |
| Ask it to change priority; see it applied | Pass — applied, confirmed in chat, tool note shown |
| See that change as a new History entry | Pass — Priority, Medium → High, Orchestration Agent, with the why |

Also confirmed: manual form edits log as the **user**; board drags log as a **status** change; applied AI drafts log as **agent-written, approved by** a named person; chat history survives a reload.

**The role gate holds, checked against the database rather than the reply text.** A Product Manager asked the agent to rewrite the Spec. The agent refused — and the `spec` row was still entirely null, with zero spec-field rows in `change_log_entry`. The refusal was real, not cosmetic.

The resulting change log for one item read:

```
priority         agent  Medium → High                    why: "Please set priority to high"
goals            user   ∅ → Cut billing support tickets…
problemStatement agent  ∅ → [stub…]                      why: "Generated draft, approved by the user"
status           user   Planning → Ready
```

`npm run lint`, `npx tsc --noEmit`, and `npm run build` all pass clean. Test data deleted; cascade deletes cleared chat and history with the work items.
## Verified against the live API (2026-08-11)

Re-run with a real `ANTHROPIC_API_KEY`. Everything previously listed as unverified now passes:

- **The live `toolRunner` + `stream: true` loop works.** Replies stream in and tool calls interleave with text correctly.
- **The model picks the right tool from natural language** — the thing the stub could not test. *"This is blocking our enterprise deal — bump it to high priority"* produced a `set_priority` call; *"We've finished scoping this, move it along to Ready"* produced a `set_status` call. Neither phrasing names a tool or a field.
- **The "only change when asked" rule holds** — the highest-risk behaviour flagged before. A plain question (*"What's the current status and priority?"*) was answered from context with **no tool call and no history entry**. The change log for that item contained exactly the two requested changes and nothing else.
- **The role gate holds through the real agent, confirmed at the database level.** A Product Manager insisting the agent rewrite the spec produced a `update_spec` call that returned *"Refused: a Product Manager cannot edit the spec view."* The `spec` row stayed null and zero spec-field rows were written — across two separate attempts.
- **The refusal-handling instruction works as written.** The agent relayed the refusal and named who could make the change: *"Engineer User can make that change. Want me to assign them the item so they can add it?"* — which is exactly what the `RULES` block asks for.
- **History is correct end to end**, including the user's own words as the `why`: `Priority · Orchestration Agent · approved by Product Manager User · Medium → High · Why: "This is blocking our enterprise deal — bump it to high priority."`

**One behaviour worth knowing.** The agent will push back on product grounds before acting, not only on permission grounds. Asked to change the spec to WebAuthn, it first objected that the field was empty and that WebAuthn contradicted the item's TOTP title — and only called the tool (and hit the gate) when the request was restated as a direct instruction. This is the "only change something when the person clearly asks" rule doing its job, and it is a good default; be aware it means a vague request may get a question rather than an edit.
